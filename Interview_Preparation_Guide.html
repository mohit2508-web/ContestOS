7. General / HR Questions

EASY
Q1: Tell me about this project.

A: "Kryptavia OS is an enterprise-grade B2B assessment platform I built solo — a single unified platform replacing 5-6 separate tools for colleges and companies. It features real-time code execution for 7 languages, 10-layer exam proctoring, a Socratic AI coding assistant, mock interviews with collaborative IDE, and multi-tenant SaaS architecture. Built with React, TypeScript, Node.js, Prisma, CockroachDB, and Redis across 94 commits with 38 database models, 29 API routes, and 50+ frontend components."

EASY
Q2: What motivated you to build this?

A: "During campus placements I saw how fragmented the tooling was — separate platforms for coding tests, quizzes, proctoring, and interviews. I wanted one unified platform covering the entire assessment lifecycle. This also let me work with advanced concepts like real-time systems, code execution engines, and exam security."

MEDIUM
Q3: What was the most challenging part?

A: "Two things: (1) The 10-layer anti-cheat stack — getting tab detection, fullscreen enforcement, webcam snapshots, and sync-cheat detection (same IP + identical answers within 500ms via in-memory sliding window) all working simultaneously without degrading exam experience. (2) The Socratic AI assistant — implementing 6-stage gate logic that rejects shallow answers while staying within a 2000-token budget."

Q4: What would you do differently?

A: "(1) Add E2E tests from day one — retrofitting tests for 29 route modules is painful. (2) Use BullMQ instead of in-memory workers for quiz autosave — current approach loses data on restart. (3) Implement WebSocket connection pooling earlier for 100+ concurrent proctor connections."

EASY
Q5: How long did this take?

A: "The core platform was built in approximately 5 days (August 24-29, 2026) with 94 commits. This was possible because I had a clear architecture plan upfront and leveraged existing libraries strategically."

MEDIUM
Q6: How did you manage scope as a solo developer?

A: "Priority matrix: Must-have (code execution, auth, contests), Should-have (proctoring, leaderboard, quiz), Nice-to-have (AI assistant, interviews, vaults). Built vertical slices — complete features from DB to UI — rather than horizontal layers. This allowed demoing working features early and iterating."

MEDIUM
Q7: How did you handle working with so many technologies?

A: "Each technology was chosen for a specific problem: CockroachDB for ACID transactions on contest scoring, Redis for O(log N) leaderboard ranking, Socket.IO for room-based WebSocket management, Prisma for type-safe database queries. I didn't choose trendy tools — I chose the right tool for each problem."

8. Technical Architecture Questions

MEDIUM
Q11: Walk me through the architecture.

A: "3-tier: Presentation: React SPA with 60+ routes, role-based guards, react-query for server state, Socket.IO for real-time. Application: Express with 29 route modules, middleware pipeline (CORS->Auth->RBAC->RateLimit), 20+ services. Data: CockroachDB (38 Prisma models), Redis (leaderboard/cache), external APIs (Piston/Judge0 for code execution)."

EASY
Q12: Why TypeScript?

A: "With 38 DB models and 29 route modules, type safety catches bugs at compile time — wrong Prisma field names, missing required fields, incorrect middleware signatures. Prisma's generated client provides full type inference. The codebase becomes self-documenting."

MEDIUM
Q13: Why CockroachDB over MongoDB or PostgreSQL?

A: "PostgreSQL-compatible SQL with distributed capabilities: (1) ACID transactions for contest scoring. (2) Horizontal scaling for growing orgs. (3) Serverless pricing. (4) Prisma works out of the box. MongoDB rejected because the data is highly relational — contests->sections->questions->options->responses need JOINs."

HARD
Q14: How does the real-time system work at scale?

A: "Socket.IO with Redis adapter. Flow: Submission evaluated -> Score to CockroachDB -> Score to Redis sorted set -> Socket.IO emits to contest room -> All clients receive update. Redis pub/sub enables multi-instance broadcasting. WebSocket binary frames for webcam snapshots. Two namespaces: /quiz-timer and /interview."

EASY
Q15: What is Redis used for?

A: "4 purposes: (1) Live leaderboard — sorted sets for O(log N) ranking. (2) Rate limiting — sliding window counters. (3) Session caching — contest tokens. (4) Socket.IO adapter — pub/sub for horizontal scaling. Gracefully degrades to in-memory if unavailable."

MEDIUM
Q16: How do you optimize bundle size?

A: "Manual chunk splitting in Vite: react-vendor, monaco-editor (5MB), framer-motion as separate chunks. react-window for virtualized lists. React.lazy() for rarely-used pages. Tree-shaking via ES modules. Monaco editor lazy-loaded only when needed."

HARD
Q17: How would you scale to 10K concurrent users?

A: "Self-hosted Judge0 on K8s with HPA. NGINX/Cloudflare load balancer. CockroachDB multi-region. Redis Cluster. Dedicated WebSocket servers. BullMQ for async tasks. Prometheus+Grafana monitoring. The architecture already supports horizontal scaling — main gap is self-hosted code execution."

MEDIUM
Q18: What design patterns did you use?

A: "Singleton (Prisma, Redis clients), Middleware Pipeline (Express chain), Strategy Pattern (code execution fallback chain), Observer Pattern (Socket.IO events), Worker Pattern (quiz autosave, web dev eval), Repository Pattern (Prisma as DAL)."

MEDIUM
Q19: How do you handle error propagation?

A: "3 layers: (1) Services throw typed errors. (2) Route handlers catch and map to HTTP status codes. (3) Global Express error middleware returns standardized JSON. Frontend: Axios interceptor catches 401s and queues token refresh. react-query provides automatic retry with backoff."

EASY
Q20: How is the project structured?

A: "Monorepo: backend/ (Express), frontend/ (React SPA), landing-page/ (marketing). Backend: routes -> middlewares -> services -> lib. Frontend: pages/ (40+), components/ (50+), contexts/, hooks/, services/. Each domain has its own route file and services."

9. Backend Deep-Dive Questions

HARD
Q21: Explain the code execution engine end-to-end.

A: "Submit -> Rate limit check (10/min) -> Code size check (500KB) -> Wrapper generation (adds test harness with stdin/stdout) -> Execute via Piston API -> If fails, try Judge0 -> If fails, local mock -> Parse output -> Compare with expected using EXACT/UNORDERED/FLOAT tolerance -> Calculate partial credit -> Save Submission with status, time, memory, per-test results -> Update leaderboard."

MEDIUM
Q22: How does the quiz autosave worker work?

A: "Background process with write-through cache: Student answers are queued in memory. Worker flushes every 3 seconds, batching up to 50 responses to CockroachDB. Reduces DB load by 95%. At most 3 seconds of data lost on crash. Critical for timed exams with thousands of answers per minute."

MEDIUM
Q23: How does the Prisma heartbeat work?

A: "Single PrismaClient stored in globalThis (survives hot reloads). Heartbeat runs SELECT 1 every 2 minutes to keep CockroachDB connections alive. withDbRetry catches P1001/P1002 errors, reconnects, retries with exponential backoff. Essential for serverless environments."

HARD
Q24: How does plagiarism detection work?

A: "MOSS-style analysis: Parse submissions to ASTs -> Extract token sequences (ignoring variable names) -> Calculate LCS ratio -> Cache with LRU -> Flag pairs with >70% similarity. Catches copy-paste with renamed variables and trivial transformations."

HARD
Q25: How does the contest assembly engine work?

A: "Faculty defines rules ('10 EASY + 5 MEDIUM from Category X') -> Engine queries QuestionBank (PUBLISHED only) -> Fisher-Yates shuffle for randomization -> Creates ContestSection with ordered questions -> IRT calibration ensures target difficulty. Saves hours of manual contest setup."

MEDIUM
Q26: How does SQL playground validation work?

A: "Defense-in-depth: (1) node-sql-parser AST validation. (2) Only SELECT allowed (no INSERT/DELETE/DROP). (3) Subquery depth limit. (4) 10K row limit via sql.js. (5) In-memory WASM SQLite — no network, no filesystem. Prevents injection, DoS, and data exfiltration."

MEDIUM
Q27: How does web dev evaluation work?

A: "Two engines: V1 (JSDOM) for fast DOM assertions. V2 (Playwright) for real browser — can evaluate canvas, animations, responsive layouts. Both run in background worker to avoid blocking API. Falls back to JSDOM if Playwright unavailable."

EASY
Q28: How do you handle environment variables?

A: ".env.example as template. .env gitignored. Key vars: DATABASE_URL, JWT_SECRET (server crashes if missing), REDIS_URL (optional), FRONTEND_URL (CORS). Postinstall hook runs prisma generate. Production via Vercel/Render dashboards."

MEDIUM
Q29: How do you map 7 programming languages?

A: "languageAdapter.ts maps names to provider-specific IDs: {cpp: {piston:'c++', judge0:54}, java: {piston:'java', judge0:62}, ...}. Each provider has different identifiers — the adapter abstracts this so the execution engine is provider-agnostic."

HARD
Q30: How would you implement sandboxed code execution?

A: "Docker containers with resource limits (1 CPU, 256MB RAM, 100MB disk, no network). seccomp profiles restricting syscalls. Read-only filesystem. Non-root user. Timeout kill via docker exec --timeout. This is how Piston/Judge0 work internally."

10. Authentication & Security Questions

MEDIUM
Q31: How does JWT refresh work?

A: "Access token (7d) expires -> 401 -> Axios interceptor queues failed request -> Sends refresh token (30d) to /api/auth/refresh -> Server validates, issues new access token -> Queued requests retry. Queue prevents concurrent refresh storms (10 simultaneous 401s would otherwise trigger 10 refreshes)."

HARD
Q32: How does break-glass access work?

A: "Super admin calls /api/admin/break-glass with target org ID + reason -> breakGlassMiddleware validates level 1 -> Temporary cross-org token (1hr expiry) -> BreakGlassAuditLog records who/what/when/why/IP -> Admin accesses target org data -> Token expires, access revoked. Critical for enterprise compliance."

MEDIUM
Q33: How does SEB integration work?

A: "3 components: (1) Config generator creates Apple plist .seb files with whitelisted/blocked URLs (blocks ChatGPT, Google, Claude, Gemini, Copilot). (2) Auto-login via URL token parameter — AuthContext reads ?token=xxx. (3) Browser verification middleware checks SEB-specific headers."

HARD
Q34: How do you prevent OWASP Top 10 vulnerabilities?

A: "10 mitigations: (1) Injection: Prisma parameterization + AST validation. (2) Auth: bcrypt 12 rounds + rate limiting. (3) Data Exposure: .env gitignored, HTTPS. (4) XXE: No XML parsing. (5) Access Control: 4 RBAC middleware. (6) Config: CORS whitelist. (7) XSS: React auto-escaping + sanitization. (8) Deserialization: TypeScript validation. (9) Vulnerabilities: npm audit. (10) Logging: Audit trails."

MEDIUM
Q35: How does rate limiting work?

A: "Redis sliding window: 10 code executions/user/min, 3 auth attempts/15min. Falls back to in-memory Map if Redis unavailable. Returns 429 with Retry-After header. Prevents abuse of external Piston/Judge0 APIs."

HARD
Q36: How do you handle GDPR compliance?

A: "Three features: (1) Article 15 export — complete data dump in JSON. (2) Article 17 erasure — compliance officer reviews, PII anonymized. (3) SOC2 audit logs — CSV export of all system actions. Data minimization: webcam frames processed and discarded, not stored."

MEDIUM
Q37: How does the JWT blacklist work?

A: "On logout, JWT's jti is added to in-memory Set. authenticateToken middleware checks blacklist before processing. Limitation: in-memory doesn't survive restarts or scale across instances. Production solution: Redis SETEX with remaining TTL."

EASY
Q38: How do you hash passwords?

A: "bcryptjs with 12 rounds (~250ms per hash). Chosen over SHA-256/MD5 because: deliberately slow (brute-force resistant), unique salt per hash (no rainbow tables), constant-time comparison (no timing attacks)."

MEDIUM
Q39: How do you handle CORS?

A: "FRONTEND_URL env var with comma-separated origins. Development: localhost:5173. Production: Vercel URL. Socket.IO configured separately. SEB exam URL added during contests. Express cors middleware sends Access-Control headers."

MEDIUM
Q40: How do you prevent XSS?

A: "5 layers: React auto-escaping, input sanitization (sanitize.ts), CSP headers via Vercel, HTTPOnly cookies, no dangerouslySetInnerHTML except for trusted admin-authored content."

12. Real-Time & Socket.IO Questions

MEDIUM
Q51: How does Socket.IO integrate?

A: "Two namespaces: /quiz-timer (exam countdown, proctor broadcasts — pause/resume/warn) and /interview (collaborative editing, code execution, hints). Redis adapter for horizontal scaling. Each contest/interview is a room for targeted broadcasting."

HARD
Q52: How do you handle WebSocket reconnection?

A: "Socket.IO built-in: exponential backoff (1s initial, 30s max, random jitter). Client re-joins room and re-fetches state from API on reconnect. Quiz autosave ensures answers are DB-persisted independently of WebSocket state."

MEDIUM
Q53: How does the live leaderboard work?

A: "Submission evaluated -> Score to DB -> ZADD to Redis sorted set -> Socket.IO emits 'score-update' to room -> Clients receive + react-query invalidates leaderboard. Fallback: full top-20 snapshot broadcast every 30s. Redis ZREVRANGE for O(log N) ranking."

EASY
Q54: What are Socket.IO rooms?

A: "Logical client groupings. Contest room (contest:123) ensures proctor warnings only reach affected candidates. socket.join() on connection, auto-leave on disconnect. Enables targeted broadcasting without global fanout."

HARD
Q55: How do you handle binary webcam data?

A: "Binary WebSocket frames: getUserMedia() -> Canvas API to JPEG blob -> Binary message (33% smaller than base64) -> Server receives and forwards to proctor -> Rendered in video grid. JPEG quality 0.6 to keep frames under 100KB. Throttled to 45s intervals."

MEDIUM
Q56: How do you prevent Socket.IO memory leaks?

A: "Auto room cleanup on empty. Max 5 connections per IP. Webcam throttled to 45s. Disconnect handler cleans up pending data. Binary frames capped at 100KB via JPEG quality reduction."

MEDIUM
Q57: SSE vs Socket.IO for notifications?

A: "SSE for notifications: simpler (unidirectional), works through proxies, auto-reconnects. Socket.IO for bidirectional: proctor actions, interview sync, leaderboard updates. Both coexist — notificationEmitter.ts bridges services to SSE stream."

HARD
Q58: How would you replace Socket.IO with native WebSockets?

A: "Use 'ws' library + native WebSocket API. Implement custom reconnection, room management (Map<roomId, Set<ws>>), binary frames directly. Use Redis pub/sub for scaling. Benefits: ~40% smaller frames, no fallback polling. Cost: ~200 lines custom code."

13. Proctoring & Anti-Cheat Questions

MEDIUM
Q59: Describe the 10-layer anti-cheat system.

A: "(1) SEB browser lockdown. (2) Fullscreen enforcement. (3) Tab-switch detection (visibilitychange). (4) Copy-paste blocking. (5) Webcam snapshots (45s). (6) Liveness/face detection. (7) Screen sharing capture. (8) Sync-cheat detection (same IP + identical answers within 500ms). (9) Proctor console (real-time dashboard). (10) Proctor actions (WARN/NUDGE/PAUSE/BLOCK/TERMINATE/DISQUALIFY via WebSocket)."

HARD
Q60: How does sync-cheat detection work?

A: "In-memory sliding window: Map<IP, Deque<{answer, timestamp}>>. When new answer arrives: get same-IP entries within 500ms window, compare answer hashes. Match = potential sync-cheat. False positive mitigation: exclude common answers. Proctor receives real-time alert with both users' details."

MEDIUM
Q61: What are the 3 non-negotiable invariants?

A: "(1) Proctoring MUST NOT degrade exam experience — all runs in background threads. (2) Exam state MUST survive network interruptions — all state persisted to DB. (3) Proctoring data MUST be encrypted at rest and in transit — webcam frames processed and discarded, not stored."

MEDIUM
Q62: What happens when a student loses internet?

A: "IndexedDB saves answers locally. Non-intrusive 'Connection Lost' banner. On reconnect, pending answers synced. No login redirect on exam routes. Server-authoritative timer continues. Follows Invariant 2."

HARD
Q63: How would you detect AI-generated answers?

A: "Keystroke dynamics (paste = sudden block vs typed = gradual), time-answer correlation (complex Q in <5s = suspicious), answer similarity (identical phrasing), SEB URL blocking, clipboard monitoring, browser fingerprinting for AI extensions."

MEDIUM
Q64: How do you handle 500+ students starting simultaneously?

A: "Server-side start timestamp queuing. Socket.IO + Redis adapter distributes WebSocket load. CockroachDB handles concurrent writes. Server-authoritative timers prevent manipulation. Quiz autosave batches responses."

EASY
Q65: What is the SEB config generator?

A: "Creates Apple plist .seb files: whitelisted exam URL, blocked AI tool URLs, disabled clipboard/screen capture, embedded auto-login token, browser security keys. Downloaded by proctor, distributed to candidates before exam."

MEDIUM
Q66: How do you handle webcam privacy?

A: "No permanent storage (processed and discarded). WSS encryption. User consent before exam. Purpose limitation (proctoring only). Violation logs reference timestamps but not images. GDPR data minimization."

MEDIUM
Q70: How does the question governance work?

A: "4-eyes review: DRAFT -> UNDER_REVIEW -> APPROVED -> PUBLISHED (or REJECTED). Every transition logged in QuestionReviewLog. No single person can inject questions into exams. Critical for exam integrity."

HARD

Remaining shown to student. Gate logic prioritizes early stages — stuck in PROBLEM/DATA_STRUCTURE exhausts budget before CODE_GEN, incentivizing independent thinking."

MEDIUM
Q72: How do 7 quiz question types work?

A: "SINGLE_SELECT (radio), MULTI_SELECT (checkbox + partial credit), TRUE_FALSE (binary), NUMERIC (tolerance range), CODE_OUTPUT (string comparison), FILL_BLANK (acceptable answers per blank), IMAGE_PATTERN (sequence selection). All support negative marking and moderator override."

MEDIUM
Q73: What are 4 scoring modes?

A: "PARTIAL (per test case credit), BINARY (all-or-nothing), ACM (max_points - penalty, penalty = wrong_subs*20 + time_minutes), DYNAMIC (max_points * 1/solve_count). Each contest section can use different modes."

EASY

15. System Design & Tricky Questions

HARD
Q76: How do you handle data consistency?

A: "Prisma transactions for multi-model writes (e.g., creating contest + mapping problems). Redis eventual consistency for leaderboard (score may lag 1-2 seconds behind DB). Quiz autosave uses write-through cache. CockroachDB ACID for all critical operations."

HARD
Q77: How would you add real-time code collaboration?

A: "Already implemented for interviews via Yjs CRDTs. For contest pair programming: (1) Create shared Yjs document per problem. (2) Socket.IO namespace /collab for sync. (3) Awareness protocol for cursor positions. (4) Both users' edits merged automatically. (5) Submission from either user counts for both."

18. Common Mistakes to Avoid

  • Don't give 1-line answers: Elaborate with specific implementation details.
